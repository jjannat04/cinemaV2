CORE WORKFLOW: SEAT BOOKING
============================

Step 1: Browse Movies
User → GET /movies → FastAPI → PostgreSQL → JSON Response

Step 2: Select Showtime  
User → GET /movies/{id}/showtimes → FastAPI → PostgreSQL → JSON Response

Step 3: View Seat Map
User → GET /seats/{showtime_id} → FastAPI → PostgreSQL → Seat Availability
           ↓
    Cleanup expired holds (in-session)
           ↓
    Return seat map with statuses

Step 4: Hold Seat (CRITICAL - Concurrency Control)
User → POST /seats/{showtime_id}/hold
           ↓
    SELECT seat FROM seats WHERE id=X FOR UPDATE  🔒 LOCK
           ↓
    Check seat.status == AVAILABLE
           ↓
    Check no active holds exist
           ↓
    CREATE seat_hold (with TTL)
           ↓
    UPDATE seat.status = HELD
           ↓
    COMMIT (releases lock)
           ↓
    Return 201 Created

Step 5: Initiate Payment
User → POST /bookings/{hold_id}/pay
           ↓
    SELECT hold FROM seat_holds WHERE id=X FOR UPDATE 🔒 LOCK
           ↓
    Check hold.is_active AND hold_expires_at > now
           ↓
    CREATE booking (status=PENDING)
           ↓
    COMMIT
           ↓
    Return 202 Accepted
           ↓
    START BACKGROUND TASK: charge_gateway()

Step 6: Background Payment Processing
Background Task → POST gateway/charge
           ↓
    Payload: {amount, booking_ref, callback_url}
           ↓
    Gateway returns 202 + payment_id
           ↓
    UPDATE booking.payment_id = payment_id
           ↓
    Gateway processes payment (2-15 seconds)
           ↓
    Gateway sends callback

Step 7: Payment Callback (Idempotent)
Gateway → POST /bookings/callback
           ↓
    Find booking by payment_id OR booking_ref
           ↓
    Check if event_id already processed
           ↓
    IF success:
        UPDATE booking.status = CONFIRMED
        UPDATE seat.status = BOOKED
        UPDATE hold.is_active = false
    IF failure:
        UPDATE booking.status = FAILED
        UPDATE seat.status = AVAILABLE
        UPDATE hold.is_active = false
           ↓
    Return 200 (always, to prevent retries)

Step 8: Background Cleanup (Every 60 seconds)
Scheduler → release_expired_holds()
           ↓
    FIND holds WHERE expires_at < now
           ↓
    UPDATE seat.status = AVAILABLE
           ↓
    UPDATE hold.is_active = false
           ↓
    CANCEL pending bookings


CONCURRENCY CONTROL MECHANISMS
===============================

1. PostgreSQL Row Locking (SELECT FOR UPDATE)
   ┌─────────────────────────────────────────────────────────┐
   │  Request 1: SELECT seat WHERE id=1 FOR UPDATE          │
   │              ✅ Lock acquired                            │
   │              Check status: AVAILABLE                     │
   │              Update status: HELD                        │
   │              COMMIT                                    │
   │              ✅ Lock released                            │
   │                                                          │
   │  Request 2: SELECT seat WHERE id=1 FOR UPDATE          │
   │              ⏳ Waiting for lock...                     │
   │              ✅ Lock acquired                            │
   │              Check status: HELD ❌                      │
   │              Return 409 Conflict                        │
   │              ROLLBACK                                   │
   └─────────────────────────────────────────────────────────┘

2. Idempotent Callback Handling
   ┌─────────────────────────────────────────────────────────┐
   │  Callback 1: event_id="abc123", payment_id="pay_456"    │
   │              ✅ Processed                                │
   │              UPDATE booking.event_id = "abc123"         │
   │              UPDATE booking.status = CONFIRMED         │
   │                                                          │
   │  Callback 2: event_id="abc123", payment_id="pay_456"    │
   │              ⚠️ Duplicate detected                       │
   │              booking.event_id == "abc123" ✅            │
   │              Return 200 (no changes)                     │
   └─────────────────────────────────────────────────────────┘

3. TTL-based Expiration
   ┌─────────────────────────────────────────────────────────┐
   │  Hold created at 10:00:00                                │
   │  HOLD_TTL_SECONDS = 300 (5 minutes)                     │
   │  Expires at 10:05:00                                     │
   │                                                          │
   │  At 10:05:01:                                            │
   │  - Request path cleanup runs                            │
   │  - Background scheduler runs                             │
   │  - Seat status: HELD → AVAILABLE                        │
   │  - Hold.is_active: true → false                          │
   └─────────────────────────────────────────────────────────┘

WHY NO MICROSERVICES?
====================

Monolithic Architecture Advantages for This Project:

1. SIMPLICITY
   ✅ Single codebase to understand and debug
   ✅ Single database transaction context
   ✅ No inter-service network latency
   ✅ Easier to build in 8-hour hackathon

2. PERFORMANCE
   ✅ No network overhead between components
   ✅ Direct database access (no service layer)
   ✅ Faster development iteration

3. CORRECTNESS
   ✅ ACID transactions across booking flow
   ✅ No distributed transaction complexity
   ✅ PostgreSQL row locks work seamlessly

4. DEPLOYMENT
   ✅ Single docker-compose up command
   ✅ No service discovery needed
   ✅ simpler monitoring and logging

5. TEAM SIZE
   ✅ Single team can manage entire codebase
   ✅ No need for independent deployment cycles

When Would Microservices Be Better?
❌ Different teams need different deployment cycles
❌ Services have vastly different scaling requirements
❌ Different technology stacks are needed
❌ System is too large for single team

Trade-offs Accepted:
❌ Independent scaling (vertical scaling sufficient)
❌ Technology flexibility (Python works for all)
❌ Fault isolation (containerization provides some)

TESTING SCENARIOS
=================

Scenario A: One Seat, Many Buyers (REQUIRED)
--------------------------------------------
Setup:
  • Pick one seat on one showtime
  • Fire 100 concurrent hold requests for that exact seat
  • Single burst (not spread over time)

Expected Results:
  • 1 successful hold
  • 99 rejections (409 Conflict)
  • 0 oversells (seat held exactly once)

How Achieved:
  • PostgreSQL SELECT FOR UPDATE row locking
  • Only one transaction can hold the lock at a time
  • Atomic check-and-update operation

Scenario B: Abandoned Hold (REQUIRED)
--------------------------------------
Setup:
  • Set HOLD_TTL_SECONDS to short value (e.g., 10)
  • Hold a seat
  • Wait for expiration
  • Try to book the same seat with different user

Expected Results:
  • Hold expires after TTL
  • Seat status changes from HELD to AVAILABLE
  • New user can successfully hold the seat
  • Timeline documented

How Achieved:
  • Background cleanup scheduler (every 60 seconds)
  • Request-path cleanup (on every seat map request)
  • TTL-based hold expiration

Scenario C: Find Breakpoint (BONUS)
------------------------------------
Setup:
  • Ramp virtual users on seat map and hold endpoints
  • Monitor p95 latency and error rates
  • Run from different machine (not same as app)

Expected Results:
  • Report where p95 latency turns upward
  • Report where errors begin
  • Explain the bottleneck (connection pool, DB contention, etc.)

How Achieved:
  • Load testing with k6 or locust
  • Monitor application metrics
  • Analyze bottleneck and explain

PRESENTATION TIPS
=================

Key Points to Emphasize:
1. Correctness over complexity - system never double-books
2. Simplicity over microservices - right choice for hackathon
3. Database-level concurrency control - PostgreSQL row locks
4. Async payment processing - required by problem statement
5. Idempotent design - handles real-world gateway behavior

Questions to Anticipate:
Q: Why not Redis for locking?
A: PostgreSQL row locks are sufficient and simpler

Q: Why monolithic not microservices?
A: Simpler, faster, adequate for hackathon scope

Q: How do you handle concurrent holds?
A: SELECT FOR UPDATE ensures only one succeeds

Q: What if gateway fails?
A: Background task marks booking failed, releases seat

Q: Why async payment?
A: Required by spec, better UX, more scalable

Q: How do you handle duplicate callbacks?
A: Event ID deduplication in database


CONCLUSION
==========

CinemaSeat is a pragmatic, correctly-functioning cinema booking system
that prioritizes:
  • Data correctness (no double-booking)
  • Simplicity (monolithic, single database)
  • Reliability (containerization, health checks)
  • Testability (unit tests, integration tests)

The system successfully handles the core challenge: high-concurrency
seat booking without selling the same seat twice.

Built for Zero to Production Hackathon
Focus: Core functionality over extensive features
